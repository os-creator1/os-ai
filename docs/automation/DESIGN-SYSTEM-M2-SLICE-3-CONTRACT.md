### 3.1 Canonical runtime theme-token API — corrected, not as the M2 contract's own prose describes it

`docs/automation/DESIGN-SYSTEM-M2-CONTRACT.md` §6.12 states `resources/js/core/theme-tokens.js` exports `getThemeToken(name)`/`getChartColors()`/`getStatusColors()` helpers. **This is not what is actually shipped.** Direct read of the real, current file confirms it defines a single global namespace, `window.PlatformTheme`, with methods: `.color(name, fallback)`, `.primary()`, `.secondary()`, `.chartPalette()` (returns an 8-element array reading `--color-chart-1` through `--color-chart-8`), `.chartNeutral()`, `.chartGrid()`, `.chartAxis()`, `.chartTooltipBg()`, `.chartTooltipText()` — each backed by one shared `getComputedStyle(document.documentElement)` reader. A repository-wide grep for `getThemeToken|getChartColors|getStatusColors` matches **only** the contract document's own prose — zero code references anywhere. The underlying architectural intent (one canonical, live-reading, runtime token source, never re-implemented per call site) **is** genuinely satisfied — just under the real name `window.PlatformTheme`, not the name the M2 contract's own text uses. **This Slice 3 contract cites `PlatformTheme` throughout, the real shipped API, not the aspirational name — future implementation must do the same.**

### 3.2 Runtime-bindings retrofit layer — status-color button classes are already covered

Direct read of `resources/scss/base/tokens/_runtime-bindings.scss` (current, full file) confirms it retokenizes, among many other rules, an explicit `@each $status, $var-base in (success: 'success', warning: 'warning', danger: 'danger', info: 'info')` loop (lines 126-142) covering `.btn-#{$status}`, `.btn-outline-#{$status}`, `.text-#{$status}`, `.bg-#{$status}`, `.border-#{$status}`, `.badge-light-#{$status}`/`.bg-light-#{$status}` — each mapped to `var(--color-status-#{$var-base})`/`var(--color-status-#{$var-base}-soft-bg)`. **This means raw Bootstrap `.btn-success`/`.btn-warning`/`.btn-info`/`.btn-danger` classes are already runtime-theme-token-live today**, independent of whether they are wrapped in the `<x-button>` component. This is a direct, load-bearing finding for §5 item 2 below: it resolves what would otherwise be a blocking API gap (`<x-button>`'s own `variant` enum, confirmed by direct read of `resources/views/components/button.blade.php`, supports only `primary|secondary|outline|ghost|danger` — no `success`/`warning`/`info`) into a non-issue for token-compliance purposes, though a real, disclosed componentization gap remains (§5 item 2).

### 3.9 CRITICAL FINDING — three of the five in-scope pages have zero authentication or authorization of any kind, with confirmed cross-tenant data exposure

**Independently verified twice** — once via research-agent audit, once via direct, first-hand file inspection of `app/Providers/RouteServiceProvider.php`, `routes/web.php`, `app/Http/Controllers/Admin/HotLeadController.php`, `app/Http/Controllers/Admin/AiAnalyticsController.php`, and `app/Http/Controllers/Admin/AiSettingsController.php` during this same drafting pass. - `GET /admin/ai-analytics`, `POST /admin/ai-analytics/book/{id}` → `AiAnalyticsController` (same: no constructor middleware, no `authorize()` call anywhere).
- `GET/POST /admin/ai-brain` → `AiSettingsController` (same: no constructor middleware, no `authorize()` call, and additionally **no `FormRequest`/validation of any kind on the write action**).

**The exact consequence, confirmed by direct trace of the actual query code, not inferred:**

- `AiSettingsController::save()` lets **any visitor, authenticated or not**, overwrite the platform's own AI system prompt and model configuration with arbitrary text — an unauthenticated write to a live, shared, platform-wide configuration surface, not merely a read-only data leak.
- Both `hot_leads` and `ai_analytics` are, in the live UI, actually reached via a link in the **customer** portal's own sidebar (`app/Helpers/Helper.php:1232-1248`, confirmed by direct read — both entries sit inside the customer section of `Helper::menuData()`, each gated only by the customer permission string `'access' => 'chat_box'`), meaning any ordinary customer with that one permission is one click away from every other customer's leads/analytics data, and the URL itself needs no authentication at all for anyone who already knows or guesses it.
- Route paths are hardcoded literal strings (`/admin/hot-leads`, `/admin/ai-analytics`, `/admin/ai-brain`) rather than built from `config('app.admin_path')`, so they do not move even on an installation that customizes its admin path for obscurity.

**What this means concretely for Slice 3, stated plainly rather than left implicit — corrected in Correction Round 1:** the state described in this section is the audit evidence found at this contract's own base SHA (`477715d011d274c066b33af44a50653f437522fd`). **It is not a target state, and it is not something Slice 3 implementation is required, or permitted, to preserve.** Human review has now decided: a dedicated security-remediation contract must be drafted, human-reviewed, human-merged, and its own implementation human-merged, **before** Slice 3 implementation may be authorized (§7).
